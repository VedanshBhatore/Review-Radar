# Decisions log

One line each: decision + why.

- Scaffolded with `create-next-app@latest` (Next 16.4.6, TS, Tailwind v4, App Router, `src/`) — matches the "latest Next.js" requirement.
- Disabled the `cacheComponents` / `partialPrefetching` experimental flags that `create-next-app` enabled by default. Checked `node_modules/next/dist/docs` (confirmed via websearch + the local docs once install finished) — Cache Components under `cacheComponents` requires route segment configs like `force-dynamic` to be replaced with `"use cache"`/Suspense boundaries, and route handlers/pages become static-by-default unless they touch a recognized dynamic API. This app's pages and POST routes are inherently request-dynamic (report-by-id, orchestration routes reading fs/Supabase, not Next's `fetch`), so the "previous model" (explicit `force-dynamic`, dynamic-by-default) is far more predictable to build against.
- Used Next 16's async `params`/`searchParams` (Promise-based) convention everywhere, since the Next-15-era sync shim was removed in 16.
- Bumped `@types/node` from `^20` to `^24` to satisfy `vitest@5`'s peer dependency range (`^22 || >=24`) — matches the installed Node 24 runtime anyway.
- Two npm installs run concurrently early on raced and silently dropped `vitest`/`@vitejs/plugin-react`/`@types/papaparse` from `package.json` (npm's own `package.json` read-modify-write isn't safe for concurrent `npm install` calls in the same directory) — re-ran sequentially. Lesson captured here so it isn't repeated: never run two `npm install`s against the same project concurrently.
- `lib/llm.ts` is the single public entry point per spec, but internals are split into `lib/llm/{mock,prompts,providers,errors}.ts` — keeps the "one interface" contract while avoiding one giant file.
- `google-play-scraper`'s `.d.ts` declares `sort` as the *enum value type* (a number) rather than the enum namespace, so `gplay.sort.NEWEST` is a real runtime value but a TS error if referenced directly (matches the task's own warning about this). Worked around with a narrow `as unknown as {NEWEST:number,...}` cast on just the `sort` property, plus `as never` on the value passed into the options object — avoids a blanket `any` and keeps the rest of the call fully typed.
- Theme merging: the model/mock only returns *which candidate indices group together* plus impact/effort; `lib/merge.ts` does the actual review-ID union, de-dup, invalid-ID dropping, double-use prevention, and "forgotten candidate kept standalone (3+ reviews)" fallback entirely in code — matches the spec's explicit requirement to never trust the LLM's own counts, and makes the trickiest logic unit-testable independent of any provider.
- RICE edits (Impact/Effort) are persisted server-side via `PATCH /api/reports/[id]/themes/[themeId]`, not just recalculated client-side — a shared report link should reflect edits a PM made, and the spec's `rice_edited` analytics event implies the edit is meant to be a real, durable action.
- `/r/[id]` reads the report directly from the store in a Server Component (`getStore().getReport(id)`) rather than through a GET API route — avoids an extra network hop for data only needed once at page load; client-side mutations (RICE edit, PRD generation, feedback) each have their own route since those are user-initiated actions after the page has loaded.
- Local JSON store (`.data/`) has no file locking / concurrent-write protection — acceptable for its stated purpose (zero-setup single-process dev), not used in production (Supabase is required there, per spec, since Vercel's filesystem is ephemeral).
- Supabase schema (`supabase/schema.sql`) stores each report/review-cache as a single `jsonb` blob keyed by id/app_id, rather than normalizing into many tables — the app's data model is already fully typed in `lib/types.ts` and always read/written as one unit per report; normalizing would add joins without adding safety. Documented inline in the SQL file too.
- Mock LLM provider's classifier initially had a keyword-fallback bug (unmatched low-rated reviews got dumped into "quality" instead of "other"), caught by actually running the demo flow in a headless browser and reading the rendered theme-detail quotes — a support complaint was showing up under "Product quality issues." Fixed the fallback to be honest (unmatched + rating<4 → "other", never a specific guessed category) and audited every demo-data template against the keyword rules for similar cross-category collisions. Kept as a reminder in `CLAUDE.md` that the mock provider is a real product surface, not a disposable test stub.
- Chart colors: didn't adopt the dataviz skill's full 8-color categorical palette, because no chart in this report actually needs 9-way categorical color — every chart with multiple bars already direct-labels each bar with its theme name, so a single uniform hue per chart (brand purple for neutral charts, danger red for the two "what's going wrong" charts: 1-star share by week, 1-star drivers) is both simpler and avoids any colorblind-safety risk entirely, per the skill's own guidance to fold excess categories into labels/facets rather than force a 9th hue.
- Playwright was installed only inside the session's scratchpad directory (its own throwaway `package.json`), never added to this project's `package.json` — it's a one-off manual browser-verification tool for this build session, not a project dependency; the project itself has no E2E test runner configured (only Vitest unit tests, per spec).
